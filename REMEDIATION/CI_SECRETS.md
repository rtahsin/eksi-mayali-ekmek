# CI & Secrets: How to store and apply secrets

This document explains how to keep secrets out of the repo and use them safely in CI (GitHub Actions) and Firebase Functions.

1) GitHub repository secrets

- Go to the repository Settings → Secrets → Actions and add secrets like:
  - `FIREBASE_TOKEN` — required by `firebase deploy --token`.
  - `FIREBASE_SERVICE_ACCOUNT` (optional) — a base64-encoded service account JSON for advanced auth.
  - Any mail/sendgrid keys, API keys, etc.

2) Use secrets in workflows

- Example: reference `secrets.FIREBASE_TOKEN` in `.github/workflows/ci.yml` (already added in this repo).

3) Setting Firebase Functions config via CI

- Option A — set config locally and deploy once:

```bash
firebase functions:config:set gmail.user="your_user" gmail.pass="your_pass"
firebase deploy --only functions
```

- Option B — set config from CI using a secret (less common): add a step before deploy:

```yaml
- name: Set functions config
  env:
    GMAIL_USER: ${{ secrets.GMAIL_USER }}
    GMAIL_PASS: ${{ secrets.GMAIL_PASS }}
  run: |
    firebase functions:config:set gmail.user="$GMAIL_USER" gmail.pass="$GMAIL_PASS" --token "$FIREBASE_TOKEN"
```

Notes:
- Using `firebase functions:config:set` stores configuration in the Firebase project, which is separate from your repo history. For highly sensitive values prefer using Google Secret Manager and the `functions.config()` integration.
- Do not echo secrets in CI logs.

4) Using service account JSON in CI (base64)

If you must use a service account JSON in CI, store it as a base64 string in `secrets.SERVICE_ACCOUNT_BASE64` and decode in workflow:

```yaml
- name: Decode service account
  run: |
    echo "$SERVICE_ACCOUNT_BASE64" | base64 --decode > serviceAccountKey.json
    export GOOGLE_APPLICATION_CREDENTIALS=$PWD/serviceAccountKey.json
  env:
    SERVICE_ACCOUNT_BASE64: ${{ secrets.SERVICE_ACCOUNT_BASE64 }}
```

5) Rotation & revocation

- Periodically rotate CI secrets and service accounts. Revoke old service account keys in Google Cloud Console.

6) Verification

- After migration of secrets to config/CI, run a staged deploy to `staging` and test functions to confirm they read config values correctly.
