# Emergency Secret Remediation & Rotation

This document describes the safe, step-by-step actions to remove committed secrets from the repository, rotate compromised credentials, and migrate secrets to safer places (Firebase functions config and CI secrets).

IMPORTANT: history-rewriting operations are destructive for collaborators. Coordinate with the team before running the history-scrub steps and ensure everyone clones afresh after the scrub.

1) Immediate local cleanup (non-destructive)

- Remove the file from the working tree and commit the removal on a short-lived branch:

```powershell
# from repo root (PowerShell)
git checkout -b remediation/remove-committed-secrets
git rm --cached functions/.env
git commit -m "chore(secrets): remove committed functions/.env"
git push -u origin remediation/remove-committed-secrets
```

Notes:
- We use `--cached` so git removes it from tracking but keeps your local copy. If you want to delete it entirely from your disk, omit `--cached`.

2) Prevent re-commit

- Add `.env` to `.gitignore` (or confirm `functions/.gitignore` contains `.env`) and commit that change.

3) Rotate compromised credentials (immediate)

- Any credentials found in `functions/.env` must be rotated immediately. For example, for Gmail credentials:
  - Change the Gmail account password and/or generate an App Password for the sending account.
  - If the account accesses production Firebase or other systems, review and rotate those tokens too.

4) Migrate secrets to secure stores

- For Firebase Functions, set secrets via environment config and not files:

```bash
# Use the Firebase CLI (authenticated) from your machine or CI
firebase functions:config:set gmail.user="your_user@example.com" gmail.pass="supersecret"
firebase deploy --only functions
```

- For CI/CD (GitHub Actions / GitLab / Azure), add secrets to the repository or organization secret store and reference them in workflows rather than checking them into code.

5) Purge secrets from git history (destructive)

Option A — Use `git filter-repo` (recommended over BFG):

```bash
# Install git-filter-repo (Python tool)
pip install git-filter-repo

# Make a backup first
git clone --mirror https://github.com/your-org/your-repo.git repo-mirror
cd repo-mirror

# Remove the file path from history
git filter-repo --path functions/.env --invert-paths

# Force-push the cleaned mirror back
git push --force --all
git push --force --tags
```

Option B — Use BFG (easier for simple cases):

```bash
# Install BFG jar (https://rtyley.github.io/bfg-repo-cleaner/)
java -jar bfg.jar --delete-files functions/.env repo.git
cd repo.git
git reflog expire --expire=now --all && git gc --prune=now --aggressive
git push --force
```

After history rewrite: ask all contributors to reclone the repo (do not pull) and verify secrets are not present in `git log`.

6) Verify remote environments

- Verify CI / deploy systems do not reference the old leaked credentials.
- Confirm new secrets are in place in the CI/hosting provider and functions work after redeploy.

7) Post-mortem & monitoring

- Rotate any potentially affected API keys and review logs for suspicious activity.
- Create a short post-mortem describing how the secret was committed and add a checklist to the repo README to avoid repeat mistakes.

8) Quick checklist (copy/paste)

```text
1) git checkout -b remediation/remove-committed-secrets
2) git rm --cached functions/.env
3) Commit and push branch
4) Add .env to .gitignore and commit
5) Rotate compromised credentials immediately
6) Migrate secrets to firebase functions:config and CI secret store
7) Coordinate and run git-filter-repo or BFG to scrub history
8) Force-push cleaned history and have all contributors reclone
9) Redeploy functions using new secrets
```
